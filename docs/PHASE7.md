# Phase 7 — Secure media and hotel verification documents

Phase 7 removes manual external image URLs from the property workflow and introduces one storage-backed media lifecycle for public hotel images and private verification documents.

## Non-negotiable media invariants

1. File bytes never travel through JSON, Base64 payloads, React state serialization, or the platform database.
2. Upload object keys are generated by the server. A client never chooses a bucket key or storage path.
3. Storage access keys and secrets are server-only configuration and are never returned by an API.
4. The browser/native client receives a short-lived presigned PUT grant for exactly one object.
5. A media record cannot become `READY` until the server verifies the exact declared content length and MIME type with storage metadata and verifies the actual file signature from a signed prefix read.
6. SVG, HTML, JavaScript, executable files, archives, and arbitrary MIME types are not accepted by the Phase 7 upload contracts.
7. Public hotel photos and private legal documents are separate visibility classes even though they share the same MediaObject lifecycle.
8. Verification documents never receive a public URL. Admin access uses a short-lived signed private GET with attachment disposition.
9. A READY verification document cannot be silently deleted by a hotel user. Upload a replacement; preserve the reviewed record for audit.
10. Completing, editing, or deleting a public hotel image advances `publishRevision` and invalidates a stale property review.
11. Approving or rejecting a verification document advances `publishRevision` because publishing readiness changed.
12. Discovery reads only READY media-backed hotel photos. PENDING_UPLOAD and DELETED media can never leak into customer results.
13. Go-live requires approved `COMMERCIAL_REGISTRATION` and `BUSINESS_LICENSE` documents in addition to the Phase 6 readiness rules.
14. `STORAGE_PROVIDER=none` is safe: the application builds and runs, but upload creation returns a service-unavailable error rather than simulating success.

## Upload lifecycle

```text
Hotel dashboard / future native app
  -> POST /api/v1/hotels/:hotelId/media/uploads
  -> platform validates permission, MIME type and size
  -> MediaObject(PENDING_UPLOAD) + HotelPhoto/HotelDocument record
  -> platform returns a short-lived signed PUT
  -> client uploads bytes directly to object storage
  -> POST /api/v1/hotels/:hotelId/media/:mediaId/complete
  -> server performs signed HEAD against object storage
  -> exact size + MIME match
  -> server performs a signed range GET for the first bytes only
  -> JPEG / PNG / WebP / PDF magic-byte signature must match the declared type
  -> MediaObject(READY)
```

Hotel images are limited to JPEG, PNG and WebP, maximum 10 MB. Verification documents are limited to PDF, JPEG and PNG, maximum 20 MB. A spoofed extension or `Content-Type` header is not sufficient: the object signature must also match.

## Verification document lifecycle

```text
PENDING_UPLOAD
  -> READY media
  -> HotelDocument(PENDING)
  -> Admin private download
  -> APPROVED | REJECTED
```

Supported Phase 7 document types:

- Commercial registration
- Business license
- Tax registration
- Bank proof
- Owner ID
- Other

The first two are mandatory for publishing readiness.

## Storage configuration

The current adapter supports AWS Signature Version 4 against S3-compatible object storage without adding an SDK dependency.

Required when `STORAGE_PROVIDER=s3`:

- `S3_ENDPOINT`
- `S3_REGION`
- `S3_BUCKET`
- `S3_ACCESS_KEY_ID`
- `S3_SECRET_ACCESS_KEY`
- `S3_PATH_STYLE`

`STORAGE_PUBLIC_BASE_URL` is required before public hotel-image uploads are issued. It should be a public bucket/CDN origin used only for public media. Private verification documents do not use this base URL.

## Bucket CORS

Because the client uploads directly to object storage, the bucket must allow the production web origin and future native networking clients to perform the signed PUT operation. For web clients, configure CORS narrowly:

- allow only trusted application origins;
- allow `PUT` for upload;
- allow the `Content-Type` request header;
- do not use wildcard origins together with credentials;
- public image delivery can be handled separately through the CDN/public media origin.

Do not solve CORS by proxying all file bytes through Next.js. Fix bucket CORS at the storage layer.

## Private downloads

`GET /api/v1/admin/hotel-documents/:documentId/download` requires a platform-admin session. The server produces a five-minute signed storage URL with attachment content disposition. The object key and storage credentials are not part of the public document API.

## Cleanup

Upload grants expire after ten minutes. The existing background worker also calls `expirePendingMediaUploads()`. Expired PENDING_UPLOAD records are marked deleted and any partially uploaded object is removed when storage is available. READY photos and reviewed documents are never touched by this cleanup.

## Deferred by design

Phase 7 does not fake malware scanning or OCR. A future scanning provider can be inserted between storage completion and READY if required by production compliance. Until then the allowlist, size checks, private-document handling, attachment-only admin download, exact storage metadata verification, and file-signature verification are the enforced controls.
